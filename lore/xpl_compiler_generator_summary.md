# Architectural Summary of the XPL Compiler Generator System

Based on the foundational paper by McKeeman, Horning, Nelson, and Wortman, the XPL compiler generator system is a translator writing system designed for structured language compilation. It is historically linked to **Auncient** programming system designs and operates through a modular compiler generator pipeline.

## 1. Core Architecture

The system is composed of three main architectural pillars:

* **XCOM**: The compiler compiler itself. It is written in XPL and compiles XPL code into target machine instructions. By using XPL to compile XCOM, it establishes a self-compiling loop (bootstrap).
* **ANALYZER**: The parser generator. It accepts a BNF grammar of the target language, verifies that it satisfies parsing constraints (specifically Mixed-Left Association / MSP rules), and outputs optimized parse tables.
* **SKELETON**: A template compiler program containing the parsing control logic. By combining the SKELETON with the parse tables generated by the ANALYZER and custom semantic actions, developers construct new language translators.

## 2. Compilation and Execution Model

The generator pipeline coordinates translation in sequence:
1. The **ANALYZER** processes the grammar rules to produce transition matrices.
2. The **SKELETON** loads these transition matrices, executing a shift-reduce parser loop.
3. Semantic stack manipulations occur during reduction phases to generate target code.
4. The generated machine instructions run under the monitor environment (**XPLSM**).

This design allows rapid compiler construction by separating syntactic parsing tables from semantic code generation routines.

## 3. Integration with HASP, BOOK, JES, and PDS

The conceptual layout of the translator writing system maps directly to mainframe job control and partition storage layers:

* **PDS and BOOK Integration**: Compiled output load modules are stored as members in Partitioned Datasets (PDS). The `BOOK` utility serves as the link-editor and directory catalog manager, formatting the binary directory blocks at offset 0 (member tracking) and registering datasets inside persistent VSAM files.
* **JES and HASP Spooling**: Compiler jobs are submitted as cards into the JES/HASP spooler queues. Jobs are scheduled and executed dynamically based on priority classes, matching the execution constraints of target programs.
* **Symbol Tables (XCOM / JCL)**: Dynamic symbol overrides (`//SET`) dynamically substitute variable cards in the execution stream, replicating XCOM's symbol table resolution passes.
* **Run-Time Monitor (XPLSM / COND)**: Step-level condition checks (`COND`) emulate the state parsing check loops inside the `XPLSM` runtime monitor, bypassing execution steps based on previous return code results.
